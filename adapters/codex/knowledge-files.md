## Codex Write Permissions

This section is installed only by the Codex adapter. Follow it before every external knowledge or learning write.

- Before each write to an existing collection, automatically run `python3 <this skill directory>/scripts/codex_memory_permissions.py check --collection <collection>`. When the check succeeds, continue without a permission prompt. The check reads persistent configuration, so if `/status` has already confirmed an exact launch-scoped root in the current Codex process, treat that session grant as effective and do not prompt again.
- If the check reports missing roots and the current session does not already have them, stop before writing and show the helper's resolved exact child path. Offer session-only access with repeatable native `codex --add-dir <exact-path>` arguments limited to roots required by the actual write. For persistent setup, first run `python3 <this skill directory>/scripts/codex_memory_permissions.py resolve-knowledge-learning-pair --collection <collection>`. A successful resolution deterministically identifies one knowledge and one learning collection in the same explicit registry domain and obtains both roots from qmd. Show both collection names and exact paths in one explicit approval request, without inferring names or paths. On approval, run the resolver's exact path-bound arguments: `python3 <this skill directory>/scripts/codex_memory_permissions.py add-roots --collection <knowledge-collection> --expected-root <knowledge-collection> <knowledge-path> --collection <learning-collection> --expected-root <learning-collection> <learning-path>`. If the counterpart is absent or ambiguous, do not form a pair; after explicit approval, run only `python3 <this skill directory>/scripts/codex_memory_permissions.py add-roots --collection <collection> --expected-root <collection> <exact-path-shown-by-check>` for the selected collection. The helper re-resolves every collection and stops without changing config if any path differs from the approved binding. If persistent configuration changes, require a new Codex process plus `/status` verification before writing. Grant exact child roots, never a broad shared parent.
- For a new external collection, select its name, exact child path, `contains` classification, and domain before creating the root or changing qmd or the shared registry. Automatically run `python3 <this skill directory>/scripts/codex_memory_permissions.py plan-new-collection --collection <new-collection> --expected-root <new-collection> <planned-exact-path> --contains <knowledge-or-learning> --domain <domain>`. This read-only plan requires the name to be absent from both catalogs, checks the roots needed for registration, and deterministically includes one existing opposite-classification counterpart in its persistent command when the same explicit domain has exactly one. If registration roots are already covered, do not ask a setup question; verify them with `/status`. Otherwise, show the helper's exact session-only restart and exact persistent command without inferring or changing names or paths, then ask which access the user wants. Run the persistent command only after explicit approval, and require a new Codex process plus `/status` after a change. Declining before a session grant leaves the collection root, qmd catalog, shared registry, and Codex config unchanged.
- Once the planned roots are effective, create the root and register the collection in both catalogs. Immediately run `python3 <this skill directory>/scripts/codex_memory_permissions.py check --collection <new-collection> --expected-root <new-collection> <planned-exact-path>`. A changed qmd path is a hard error requiring a fresh plan and approval. If the binding is unchanged and the check reports only roots already confirmed by `/status` for this process, the session grant is effective. Do not create or modify collection content until this bound check succeeds or `/status` confirms those exact session roots. If planning finds one-sided qmd/registry state, stop and guide the user through repair instead of treating the name as new.
- Do not use `$memory-reindex` or `memory_bank.py reindex` for knowledge or learning files. After the editor review window settles, healthy trusted lifecycle hooks normally flush the affected collection. If those hooks are absent, disabled, untrusted, interrupted, or fail, request one-shot approval for the exact `qmd update` command outside the spawned-command sandbox. After it succeeds, request separate one-shot approval for the exact `qmd embed -c <collection>` command outside that sandbox, then verify retrieval through qmd MCP. The harness invokes both commands; do not ask the user to type them unless native approval is unavailable, and do not create a persistent qmd, Python, or shell rule.

### Example

For a default install, before writing `my-product-knowledge`, run `python3 ~/.agents/skills/knowledge-files/scripts/codex_memory_permissions.py check --collection my-product-knowledge`. If it succeeds, continue silently. If it reports a missing root and no exact session grant is active, run `python3 ~/.agents/skills/knowledge-files/scripts/codex_memory_permissions.py resolve-knowledge-learning-pair --collection my-product-knowledge`. Suppose the resolver returns `my-product-knowledge` at `/Users/example/Documents/MyProduct/knowledge` and `my-product-learning` at `/Users/example/Documents/MyProduct/learning`; ask, "Add persistent Codex write access to these two exact collection roots?" and show both mappings. Only after approval, run `python3 ~/.agents/skills/knowledge-files/scripts/codex_memory_permissions.py add-roots --collection my-product-knowledge --expected-root my-product-knowledge /Users/example/Documents/MyProduct/knowledge --collection my-product-learning --expected-root my-product-learning /Users/example/Documents/MyProduct/learning`. These values are illustrative: always use this installed skill's actual helper path and the resolver's exact output, and never substitute the shared parent `/Users/example/Documents/MyProduct`. After a changed config, stop and require a new Codex process plus `/status`.

Before creating a new `my-product-learning` collection at `/Users/example/Documents/MyProduct/learning`, run `python3 ~/.agents/skills/knowledge-files/scripts/codex_memory_permissions.py plan-new-collection --collection my-product-learning --expected-root my-product-learning /Users/example/Documents/MyProduct/learning --contains learning --domain my-product`. If access is missing, show and follow one of the helper's exact commands; do not register first. After the approved roots are effective, create the root, register both catalogs, and run `python3 ~/.agents/skills/knowledge-files/scripts/codex_memory_permissions.py check --collection my-product-learning --expected-root my-product-learning /Users/example/Documents/MyProduct/learning` before writing content.
